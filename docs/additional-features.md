# Phase 6: дополнительные функции

В этом этапе добавлены listing, usage и логические квоты. Они решают конкретные
пробелы текущего локального backend: клиент может найти ключи без доступа к диску,
проверить объём данных и ограничить рост опубликованных объектов. Общий токен
по-прежнему даёт доступ ко всему экземпляру; пользовательские ACL не появились.
Формат файлов, PUT/DELETE и скачивание не менялись, миграция данных не нужна.

## Список объектов

```http
GET /abc?prefix=photo-&limit=100
GET /abc?prefix=photo-&limit=100&after=photo-0100.jpg
```

Для обоих запросов требуется обычный `Authorization: Bearer ...`.
`GET /{bucket}` и `HEAD /{bucket}` теперь поддерживаются; завершающий `/` допустим.
Параметры:

| Параметр | Значение |
|---|---|
| `prefix` | Необязательный, регистрозависимый префикс ключа, UTF-8, до 255 байт, без разделителей пути и управляющих символов |
| `limit` | Размер страницы 1..1000, по умолчанию 100 |
| `after` | Необязательный логический ключ; вернуть ключи строго после него |

Ключи сортируются по строковому порядку Go (байты UTF-8), без locale/case folding.
Запрос возвращает XML `ListObjectsResult`: `Bucket`, `Prefix`, `After`, `Limit`,
`IsTruncated`, при наличии продолжения — `NextAfter`, затем повторяющиеся
`Contents` с `Key`, `Size`, `ContentType`, `LastModified`. `Key` — логический ключ,
без физического пути или исторического `data/` из старого metadata endpoint.
Checksum не вычисляется при listing; для ETag используйте HEAD объекта.

Если `IsTruncated=true`, передайте `NextAfter` в следующем `after`, сохранив
`prefix`. Значения нужно URL-кодировать: `+`, `&`, `#`, Unicode и другие символы
могут иметь особое значение в query string. Удаление объекта, указанного в `after`,
не ломает продолжение: marker не требует существующего файла.

Одна страница согласована под read lock. Несколько запросов страниц **не являются
единым snapshot**: новый ключ перед marker может не попасть в дальнейшую выдачу,
изменённые/удалённые объекты видны по состоянию следующей страницы. Для неизменного
снимка используйте остановленный источник или отдельную процедуру snapshot.

Пустой бакет/отсутствующий префикс — 200 с пустым списком; неизвестный бакет — 404.
Неверные, дублированные или неизвестные параметры — 400. HEAD выполняет тот же
поиск и возвращает длину XML без тела. Это собственный API, не S3 ListObjectsV2.

Реализация сканирует RAM-индекс и удерживает не больше `limit+1` элементов в heap:
дополнительная память O(limit), время O(N log(limit+1)). Read lock во время скана
может задерживать публикацию/удаление при очень большом бакете; отдельный
сортированный индекс оправдан, если измерения рабочего окружения покажут проблему.

Замер 10 итераций на Apple M5/macOS arm64, Go 1.25.12, `limit=100`:

| Размер синтетического индекса | ns/op | B/op | allocs/op |
|---|---:|---:|---:|
| 1 000 объектов | 91 088 | 23 606 | 108 |
| 100 000 объектов | 1 242 496 | 23 606 | 108 |

Это только in-memory listing, без HTTP, диска и конкурирующих записей; размер
самого уже существующего индекса исключён. Не оценка production throughput.

```sh
go run ./tests ./internal/storage -run '^$' -bench '^BenchmarkListObjects$' -benchtime=10x -benchmem
```

## Использование и квоты

`GET /-/usage` возвращает авторизованный XML `StorageUsage`:

- `StoredBytes`: сумма размеров опубликованных объектов;
- `Objects`: число объектов, включая пустые;
- `Buckets`: число бакетов, включая пустые;
- `MaxStorageBytes` и `MaxObjects`: настроенные лимиты, 0 означает отсутствие лимита.

HEAD поддерживается; остальные методы возвращают 405. Ответ — согласованный
снимок счётчиков под read lock. Они обновляются вместе с публикацией/удалением,
поэтому endpoint не сканирует диск. После restart значения восстанавливаются
при существующем сканировании файлов, а не из CSV или отдельной базы счётчиков.

Новые параметры запуска (по умолчанию оба 0, прежнее поведение сохраняется):

```sh
# Например: 10 GiB опубликованных файлов и не больше 100 000 объектов.
./triple-s --max-storage-bytes 10737418240 --max-objects 100000
```

Остальные настройки запуска и `TRIPLE_S_TOKEN` остаются необходимыми.
Квоты задаются для всего экземпляра, а не для пользователя/бакета. Значения
неотрицательны; верхние пределы конфигурации — 2^60 байт и 2^40 объектов.
Включённый `--max-object-bytes` продолжает отдельно ограничивать каждый upload.

Проверка выполняется после потоковой записи staging, **до rename** под той же
блокировкой, что и публикация. Перезапись учитывает размер текущей версии,
а не версии на момент начала запроса. Конкурентные uploads не обходят квоту.
Превышение возвращает HTTP 409 с `storage quota exceeded`, staging удаляется,
старый объект сохраняется. Ошибка публикации до rename не меняет счётчики;
после добавления журнала ошибка после commit decision требует recovery (503).
RAM/usage публикуются только после завершения транзакции; при restart решение
воспроизводится до восстановления счётчиков. См. [протокол фиксации](object-commit.md).

Удаление освобождает логическую квоту. Перезапись не увеличивает число объектов.
Если лимит после restart стал ниже существующего использования, данные не
удаляются и запуск разрешён. Запрещён дальнейший рост в превышенной размерности:
разрешены удаление и замены, не увеличивающие превышенный показатель. Например,
при превышенном лимите байт можно уменьшить файл, даже если общий размер всё ещё
выше лимита. Лимиты байт и количества проверяются независимо.

**Это не квота физического диска.** Staging, служебные файлы, размер блоков FS,
backup и удалённые/заменённые версии с открытым download descriptor не входят
в `StoredBytes`. Прежде чем отказать по квоте, сервер может прочитать полный
upload. Для staging нужен запас до `max-uploads * (max-object-bytes + 1)` байт;
открытые старые версии и остальные файлы требуют дополнительного места.
Количество пустых бакетов не ограничивается `max-objects`. Для жёсткой защиты
диска используйте также квоту/лимит файловой системы и мониторинг свободного места.

## Observability и проверки

В существующих метриках/JSON-логах появились фиксированные operation labels
`list_objects` и `usage`. Quota 409 учитывается как ошибка upload. Prefix, marker,
имена объектов и содержимое XML не включаются в telemetry.

Добавлены проверки:

- listing: сортировка, prefix/Unicode, pagination, удалённый marker, пустая выдача,
  400/404, HEAD, auth, отмена и закрытый Store;
- quota: глобальные лимиты между бакетами, empty objects, overwrite/delete,
  неуспешный rename, сохранение старых данных, restart с пониженным лимитом;
- одновременная публикация 8 uploads по лимиту байт, количества и одного ключа;
- восстановление usage после process crash и backup/restore;
- передача options/context через service, сохранение errors.Is;
- новые endpoints и quota 409 через реальное HTTP-соединение.

Полная матрица `go run ./tests -race -tags=integration,stress -count=1 -timeout=5m ./...`
прошла локально; vet и сборки macOS/Linux также прошли. Existing CI подхватывает
новые тесты автоматически. На Linux исполнение тестов проверит GitHub runner.

## Остальные кандидаты

| Функция | Польза и необходимость | Сложность / риск | Решение |
|---|---|---|---|
| Resumable/multipart upload, upload progress | Восстановление больших передач после обрыва; progress уже можно считать на клиенте по отправленным байтам | Высокая: сессии, квоты staging, expiry и crash recovery | Отложено до подтверждённой потребности; атомарный streaming PUT сохранён |
| Presigned URLs | Снижение нагрузки при внешнем object storage | Средняя/высокая: отдельная модель полномочий и S3 backend | Для текущего локального backend не внедряется |
| Versioning | Восстановление предыдущего содержимого | Высокая: формат хранения, retention, quota и миграция | Отдельный этап с согласованной политикой хранения |
| Пользовательские metadata / object tags | Поиск и классификация | Средняя: атомарная связь blob/metadata и recovery | Базовые metadata уже есть; произвольные поля пока не добавлены |
| Deduplication | Экономия при повторяющихся данных | Высокая: reference counts, GC и усложнение восстановления | Сначала измерить долю дублей |
| Image optimization / thumbnails | Быстрые превью изображений | Высокая: типы файлов, лимиты декодирования и фоновые jobs | Нет подтверждённой image-бизнес-логики |
| TTL / автоматическое удаление | Ограничение срока хранения | Средняя/высокая, риск потери данных при неверной политике | Автоматическое удаление не включено; сначала определить retention |
| Batch mutations | Меньше HTTP-запросов для массовых изменений | Средняя: частичный успех, retry/idempotency и limits | Listing даёт основу, batch delete отдельно после выбора семантики |
| Долговечный audit trail | История действий для расследований | Средняя/высокая: отдельное хранение, retention и защита от изменения | Текущие request events не объявляются полноценным audit trail |

Эти возможности не реализованы автоматически: некоторые требуют новой модели
хранения или бизнес-решений. Завершение Phase 6 относится к трём функциям выше.
