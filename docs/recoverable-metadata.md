# Восстановимое хранение metadata объектов

Metadata объектов теперь сохраняется между запусками. В каждой записи находятся
логический bucket/key, размер, MIME, LastModified и SHA-256. Данные файла остаются
источником истины; это восстановимый дисковый индекс производных полей, а не
независимая база пользовательских атрибутов. Произвольные custom metadata/tags
этот этап не добавляет.

## Формат и публикация

Для каждого объекта создаётся отдельная запись:

```text
.triple-s/metadata/<sha256(bucket + NUL + key)>.json
```

Каталог имеет права 0700, записи — 0600. Версионированный JSON envelope содержит
версию 1, payload и SHA-256 payload. Payload включает metadata и локальный
fingerprint файла: device, inode, ctime с наносекундами. Проверяются также размер,
mtime, MIME и логический ID. Hash имени записи избегает ограничений длины/символов
ключа и не используется как путь, предоставленный клиентом.

При PUT файл по-прежнему записывается в staging, синхронизируется и публикуется
атомарным rename. Затем под той же блокировкой публикации metadata записывается
в `.triple-s/metadata-<random>`, выполняются file sync, close, rename в конечную
запись и directory sync. Успешный PUT означает, что обе последовательности
синхронизации завершились. Существующий HTTP/API-контракт не изменён.

После добавления [согласованной фиксации](object-commit.md) PUT/DELETE используют
журнал решения, записываемый до изменения blob. Ошибка завершения после решения
переводит хранилище в `recovery required` (503) до restart. Replay сначала завершает
зафиксированную операцию, затем запускается обычное восстановление metadata.
Описание ниже относится к восстановимым derived records, а не к авторитетному
журналу: повреждённый journal нельзя автоматически пересоздавать или удалять.

## Восстановление при старте

После эксклюзивной блокировки каталога сервер:

1. Проверяет private metadata directory и типы файлов. Symlink, неизвестное имя
   или нестандартный тип — ошибка запуска, без чтения/удаления внешних целей.
2. Удаляет только известные временные `upload-*`, `bucket-*`, `metadata-*` записи.
3. Сканирует реальные объекты, проверяет envelope/digest/версию и fingerprint.
4. Использует валидную запись, включая SHA-256, без полного чтения объекта.
5. Для отсутствующей, обрезанной, слишком большой, повреждённой или устаревшей
   записи читает объект потоково, пересчитывает SHA-256 и атомарно сохраняет запись.
6. Восстанавливает RAM-индекс и usage из файлов; удаляет metadata, у которой нет
   соответствующего опубликованного объекта.

Записи читаются с лимитом 16 KiB. Версия формата >1 вызывает явный отказ запуска:
старый код не должен молча уничтожать metadata будущего формата. Ошибки чтения,
прав или диска не маскируются под отсутствие записи. Если пересоздать нужную
запись не удалось, запуск завершается ошибкой. Содержимое blob не переписывается.

Проверка inode/ctime защищает от использования metadata старой версии, даже
если новый файл имеет прежние размер и mtime. Во время полного пересчёта повторно
проверяется fingerprint: изменение файла во время чтения не принимается как
согласованный результат. Внешнее редактирование файлов при работающем сервере
по-прежнему не поддерживается.

## Обновление и backup

Существующие каталоги совместимы с новой сборкой. При первом старте записи
создаются автоматически, без перемещения/преобразования blob. Первый старт
потребует чтения всех объектов без валидных записей; планируйте время и свободное
место. При прерывании старта следующая попытка продолжит безопасно: завершённые
записи переиспользуются, временные очищаются.

После обычного restart SHA-256 уже есть в RAM-индексе; первое скачивание обычно
не требует повторного хеширования. Обновлённое поведение заменяет прежнее ленивое
вычисление checksum первого GET/HEAD.

Offline backup всего `--dir` включает metadata. При восстановлении на новый
каталог/диск fingerprint файлов меняется, поэтому записи будут пересчитаны до
приёма запросов. Проверка tar checksum и контрольных объектов остаётся обязательной;
инструкция — [backup/restore](backup-restore.md).

Старые бинарники, которые не знают `.triple-s/metadata`, не совместимы с новым
служебным layout. Для отката используйте отдельную проверенную offline-копию,
сделанную до обновления, и не запускайте разные версии на одном каталоге.
Production-каталог при реализации не открывался и не мигрировался: изменения
проверялись только на временных тестовых данных.

## Гарантии и ограничения

- Записи производные: их отсутствие/повреждение восстанавливается из файлов.
  Они не могут восстановить удалённое содержимое объекта.
- Envelope checksum обнаруживает случайное повреждение metadata. Это не MAC
  и не защита от владельца файловой системы, способного изменить payload/digest.
- Fingerprint не заменяет полный integrity scrub. Повреждение носителя без
  изменения stat-полей может остаться незамеченным до отдельной проверки SHA-256.
- При копировании, восстановлении или редактировании файлов вне сервера metadata
  перестраивается из текущих байтов. Она не служит независимым immutable checksum
  manifest для доказательства целостности backup. Храните отдельный checksum
  архива/контрольный manifest в доверенном месте.
- Авторитетное время создания бакета остаётся в `.bucket.json`. Повреждение этого
  файла по-прежнему требует backup/ручного разбора: точную дату нельзя надёжно
  вывести из содержимого объектов. Bucket LastModified остаётся производным.
- Metadata требует дополнительного файла/inode на объект и нескольких sync при
  записи; публикация может занимать больше времени. Логические квоты metadata
  и staging не учитывают — необходим запас физического диска.
- Startup остаётся O(число объектов) с чтением небольших records/MIME-префиксов;
  только повреждённые/устаревшие записи требуют полного чтения blob. При repair
  память не растёт пропорционально размеру отдельного файла.
- Поддерживаются Linux/macOS. Process-crash tests не доказывают поведение при
  отключении питания или неисправном диске; гарантии sync зависят от файловой системы.

## Проверки

Добавлены тесты сохранения и повторного использования metadata без перезаписи,
восстановления после потери directory/record, truncated/oversized JSON, порчи
checksum, изменения blob с прежним размером/mtime, отказа metadata publication,
защиты от symlink/неизвестных файлов и будущей версии формата.

Process-crash сценарии: обрыв upload, смерть после blob rename, перед metadata
rename, после metadata rename и после unlink blob до очистки metadata. Проверяются
фактическое содержимое, SHA-256, usage, очистка staging и отсутствие воскрешения
удалённых файлов. Прежние quota/concurrency, backup, HTTP/TLS и large-file тесты
проходят с новой реализацией.

```sh
go run ./tests -race ./...
go run ./tests -race -tags=integration,stress -count=1 -timeout=5m ./...
go run ./tests ./internal/storage -run '^$' -bench '^BenchmarkMetadataRecovery$' -benchtime=10x -benchmem
```

Локальная полная матрица, vet и сборки macOS/Linux прошли. Замер до добавления
журнала согласованной фиксации: 10 итераций,
Apple M5/macOS arm64, Go 1.25.12, один файл 16 MiB, прогретый кеш ОС:

| Open + проверка metadata + Close | ns/op | B/op |
|---|---:|---:|
| Валидная запись | 599 521 | 21 068 |
| Пересоздание отсутствующей записи | 25 288 037 | 55 179 |

Это сравнение двух режимов новой реализации; не обещание производительности
production и не сравнение общей скорости PUT с прежним форматом.
