# Многопользовательский доступ

## Контракт

Все прежние URL и XML-представления сохранены. `Authorization: Bearer <token>`
теперь определяет пользователя и его пространство хранения.

| Учётные данные | Без X-Storage-User | С X-Storage-User: alice | /-/metrics |
| --- | --- | --- | --- |
| alice, role=user | Только бакеты/объекты alice | 403, даже для собственного ID | 403 |
| bob, role=user | Только бакеты/объекты bob | Только бакеты alice, выданные через grants; иначе 403 | 403 |
| role=admin или прежний TRIPLE_S_TOKEN | Прежнее административное пространство | Пространство alice | Общие метрики процесса |
| Нет токена, неверный или disabled | 401 | 401 | 401 |

Одинаковые имена бакетов и объектов у разных пользователей независимы.
Без явного grant пользователь не может перечислять, читать metadata, скачивать,
перезаписывать или удалять данные другого пользователя. Отсутствующий в собственном пространстве
объект возвращает 404 независимо от его наличия у других пользователей.
`GET /-/usage` доступен владельцу и администратору для выбранного пространства.
Для приглашённого пользователя он закрыт (403), чтобы не раскрывать приватные
бакеты владельца. Listing при совместном доступе фильтруется по grants.
Администратор выбирает пространство явно; объединённого списка всех бакетов нет.
Неизвестный, пустой или повторённый заголовок выбора у администратора даёт 400.

Совместный доступ задаётся явно для отдельных бакетов. Администратор остаётся
полностью доверенным и управляет реестром прав; API выдачи разрешений клиентам нет.

## Реестр пользователей

Новый аргумент: `--users-file /absolute/path/users.json`. Файл читается при старте,
должен быть обычным файлом с правами 0600 (допустимо 0400), не symlink, до 1 MiB.
JSON строго проверяется; неизвестные поля, неверная версия, дубли ID/хешей,
неверные роли и повреждение приводят к отказу запуска. Максимум 1000 записей.

Формат (значение в угловых скобках нужно заменить настоящим SHA-256):

```json
{
  "version": 1,
  "users": [
    {
      "id": "alice",
      "role": "user",
      "token_sha256": "<64 lowercase hex characters>",
      "disabled": false
    }
  ]
}
```

ID: `[a-z][a-z0-9_-]{0,63}`. ID постоянный: его нельзя менять при ротации токена
или передавать другому человеку. Он определяет владельца данных даже после
удаления записи из реестра. Храните disabled-записи вместо повторного использования ID.
Роль `admin` даёт доступ ко всем пространствам, включая disabled-пользователей.
Администратор из файла может выбрать и собственное пространство своим ID.

Используйте случайные токены с энтропией минимум 256 бит. Это API-токены, не пароли:
быстрый SHA-256 не защищает слабые человеческие пароли от перебора. В запросе токен
должен иметь минимум 32 байта. В реестре сохраняются только хеши; они сравниваются
с SHA-256 предъявленного токена. Сами токены и реестр не должны попадать в Git.
Реестр авторитетен для прав: его изменение доступно только оператору сервера.

Пример создания нового реестра и отдельных приватных файлов токенов. Выполняйте
в приватном каталоге конфигурации вне `--dir`, не внутри репозитория. Скрипт не
печатает секреты и отказывается перезаписывать существующие файлы:

```sh
umask 077
python3 - <<'PY'
import hashlib, json, os, secrets
users = []
for user_id, role in [("operator", "admin"), ("alice", "user"), ("bob", "user")]:
    token = secrets.token_hex(32)
    fd = os.open(user_id + ".token", os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
    with os.fdopen(fd, "w") as f:
        f.write(token + "\n")
    users.append({"id": user_id, "role": role,
                  "token_sha256": hashlib.sha256(token.encode()).hexdigest()})
fd = os.open("users.json", os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as f:
    json.dump({"version": 1, "users": users}, f, indent=2)
PY
```

Передавайте каждому клиенту только его токен через защищённый канал/secret manager.
Запуск: `triple-s --dir /absolute/path/data --users-file /absolute/path/users.json`.
Прежний `TRIPLE_S_TOKEN` необязателен при наличии активного пользователя в файле.
Если он остаётся заданным, это дополнительный административный credential.
Одинаковый токен в переменной и реестре запрещён. Без активных credentials сервер
не запускается. TLS/ограничения внешнего HTTP остаются прежними.

Ротация: создайте новый случайный токен, замените только `token_sha256` у прежнего
ID, сохраните реестр с приватными правами и перезапустите сервер. Старый токен
перестанет работать после перезапуска. Отзыв: `disabled: true` и перезапуск.
Горячей перезагрузки и перекрывающихся токенов одного ID нет. Запросы, уже принятые
до остановки, могут завершиться при штатном shutdown.

## Хранение, миграция и восстановление

Существующие данные не перемещаются и не назначаются новым пользователям.
Они доступны только администратору без заголовка выбора. Если прежний общий токен
был роздан клиентам, замените/уберите его и выдайте каждому отдельный токен:
сохранение известного клиентам административного токена отменит ожидаемую изоляцию.

Пространства расположены в `--dir/.triple-s/tenants/<sha256(user-id)>/`.
Каждое использует существующий Store: отдельные бакеты, индекс, metadata, журнал
фиксации, файловая блокировка и восстановление. HTTP выбирает конкретный Store
после аутентификации; ID пользователя не конкатенируется с именем бакета/объекта.
Имена каталогов проверяются, symlink и неприватные каталоги не допускаются.
Верхняя блокировка удерживается до закрытия пространств после остановки handlers.

При включённых пользователях на старте восстанавливаются все существующие
пространства, включая исключённые из реестра. Повреждение журнала блокирует запуск
вместо молчаливого удаления данных. Ошибка фиксации во время работы блокирует
только соответствующий Store. Отзыв/удаление учётных данных не удаляет файлы.

Offline backup всего `--dir` включает все пространства, staging и журналы.
Отдельно сохраняйте актуальный реестр и credentials через защищённый механизм.
Для восстановления сохраняйте прежние ID. Не восстанавливайте старые права/токены
без проверки: это может вновь активировать ранее отозванный доступ.
Отсутствующий/повреждённый реестр не восстанавливается из объектов автоматически.
Предыдущий бинарник может не понимать каталог tenants; rollback — только через
отдельную offline-копию и совместимую версию.

## Ресурсы и границы

`--max-storage-bytes` и `--max-objects` применяются **к каждому пространству**,
включая прежнее административное; это не суммарная квота всего диска.
`--max-object-bytes` одинаков для всех. Общие HTTP-ограничения `--max-uploads` и
`--max-downloads` ограничивают процесс независимо от числа пользователей. Upload
admission включает PUT бакета; download admission включает GET/HEAD listing/usage.
Административные метрики исключены из download admission.

Индексы всех пространств находятся в памяти; суммарное число объектов определяет
её потребление. Лимиты файловой системы и свободное место остаются обязательными
операционными ограничениями. Rate limiting, индивидуальные квоты и объектные ACL сюда не входят.
Read/write permissions действуют на уровне выбранного бакета. Изоляция защищает HTTP-клиентов;
оператор с правом записи в каталоги данных/реестр остаётся доверенной стороной.
Встроенной регистрации пользователей, password login и внешнего IdP нет.

## Проверки

- Матрица HTTP: одинаковые имена у alice/bob/admin; чужие GET/HEAD/metadata/PUT/DELETE,
  listing и usage, подмена scope, disabled token, доступ к metrics.
- Конкурентная запись одинаковых имён и общий admission между пользователями.
- Ротация с постоянным ID, повторное открытие, offline tar backup/restore.
- Незавершённая фиксация в одном пространстве, независимая запись в другом,
  последующее восстановление обоих; отказ на symlink/неверных namespaces.
- Реальный subprocess HTTP: запуск с users-file, изоляция, admin scope,
  штатная остановка и повторный запуск.

Команда: `go run ./tests -race -tags=integration,stress -count=1 -timeout=5m ./...`.
Тесты используют только локальные вымышленные credentials.

## Совместный доступ к отдельным бакетам

В запись **получателя доступа** (например, bob) добавьте поле `grants`:

```json
"grants": [
  {"owner": "alice", "bucket": "shared", "permission": "read"},
  {"owner": "alice", "bucket": "incoming", "permission": "write"}
]
```

Владелец должен существовать в том же реестре. ID не могут повторно назначаться
другим людям. `grants` необязателен: старые реестры сохраняют строгую изоляцию.
Grant самому себе и grants у admin запрещены как избыточная конфигурация.
Неизвестный owner, неверное имя бакета/permission и повтор owner+bucket отклоняют
запуск. Допускается до 256 grants на пользователя и 4096 суммарно.

После перезапуска bob использует **собственный токен** и заголовок
`X-Storage-User: alice`. Без этого заголовка запросы продолжают обращаться к
собственному пространству bob. Токен владельца передавать не нужно.

| Операция в выбранном пространстве владельца | read | write |
| --- | --- | --- |
| GET / — список только разрешённых бакетов | Да | Да |
| Listing файлов разрешённого бакета | Да | Да |
| GET/HEAD объекта, metadata, Range/conditional download | Да | Да |
| PUT объекта, включая перезапись | 403 | Да |
| DELETE объекта | 403 | Да |
| Создание/удаление самого бакета | 403 | 403 |
| Обращение к соседним неразрешённым бакетам | 403 | 403 |
| GET/HEAD /-/usage и /-/metrics | 403 | 403 |

`write` **включает чтение и удаление файлов**. Назначайте `read`, если изменение
данных не требуется. Владелец и admin сохраняют управление самим бакетом.
Данные не копируются: чтение/запись идут в Store владельца с его журналом,
блокировками, квотой и usage. Общие ограничения параллельных запросов сохраняются.
Для запрещённого бакета одинаковый 403 возвращается и при его отсутствии, поэтому
подбор имён не раскрывает его существование. Для разрешённого отсутствующего
бакета/объекта возвращается обычный 404.

Права привязаны к паре **owner ID + имя бакета**, а не к его конкретному созданию:
если владелец удалит и заново создаст бакет с тем же именем, grant останется.
Перед повторным использованием имени проверьте и при необходимости отзовите grants.
Отключение токена владельца не отзывает отдельные grants получателей: это разные
решения. Для отзыва общего доступа удалите соответствующий grant и перезапустите.
Уже принятые операции могут завершиться при штатной остановке.

Прежнее административное пространство без owner ID не расшаривается этим
механизмом. Для таких данных нужен явный перенос выбранных объектов в пользовательское
пространство оператором; автоматической миграции и выдачи прав всем клиентам нет.

`shared_access_test.go` проверяет матрицу разрешений, соседние бакеты, собственные
одноимённые объекты, Range, фиксацию конфигурации при старте, restart и отзыв grants.
Реальный HTTP integration также читает grants из users-file и проверяет read-only
доступ после перезапуска.

## При использовании --backend cluster

Всё описанное выше о файле registry и restart относится к local backend.
В кластере `triple-s-cluster sync-users --users-file ...` атомарно публикует реестр
в PostgreSQL, и новые запросы всех реплик сразу используют актуальные права.
TRIPLE_S_TOKEN на API запрещён; admin также задаётся в общем реестре.
[Настройка и перенос данных](horizontal-scaling.md).
