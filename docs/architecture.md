# Архитектура после Phase 2

## Границы компонентов

```text
main: config.Parse → storage.Open → service.New → httpapi.New → HTTP server
                                     ↑                 ↑
                              service.Repository   httpapi.Operations
```

| Пакет | Ответственность |
|---|---|
| `internal/config` | Флаги, проверка настроек, один абсолютный DataDir, общие лимиты |
| `internal/objectstore` | BucketID, ObjectKey, ObjectID, метаданные, ошибки и правила допустимых имён |
| `internal/service` | Прикладные операции, ранняя валидация, context, ошибки с контекстом операции |
| `internal/httpapi` | Маршруты, общий Bearer token, HTTP-лимиты, XML DTO, status codes |
| `internal/storage` | Локальные файлы, индекс, блокировки, atomic commit, recovery и дисковый формат |
| `main` | Сборка зависимостей и lifecycle; только здесь читается окружение процесса |

HTTP-пакет не импортирует файловый backend. Сервис не импортирует HTTP или
файловую систему. Интерфейсы определены у потребителей: transport → application
и application → repository. Их можно подменять в тестах без диска и сети.
Отдельные интерфейсы для каждой функции, универсальный ORM и DI-контейнер не нужны.

`service.Repository` принимает типизированные идентификаторы и context во всех
операциях, включая чтение. Он предоставляет **завершённые операции**, а не
раздельные команды «записать файл» и «записать metadata». Текущему локальному
backend необходимо сохранять общий commit point и блокировки для этих действий.
Иначе отдельные BlobStore и MetadataStore вновь создадут проблему двух независимых
записей, устранённую в Phase 1. Конкретная реализация разделена по файлам:
`bucket.go`, `object.go`, `metadata.go`, `recovery.go`, lifecycle в `storage.go`.

## Идентификаторы и форматы

- `BucketID` — логическое имя бакета.
- `ObjectID{Bucket, Key}` — пара, идентифицирующая объект. Одинаковые ключи в
  разных бакетах различаются; путь filesystem в идентификатор не входит.
- Доменные структуры не содержат XML/JSON-тегов, физического DataDir или
  строковых статусов `Active` / `Marked for deletion`.
- Пустота бакета определяется по индексу, а в старую строку статуса переводится
  только при создании XML-ответа.
- Префикс `data/` в `ObjectKey` остаётся только в HTTP DTO ради совместимости.
- `.bucket.json` читает/пишет отдельная структура дискового формата. Phase 1
  поля `Name` и `CreationTime` сохранены; старые дополнительные поля игнорируются.

Имена пока остаются идентификаторами. Случайные UUID/BlobID без переименования,
версий объектов или отдельной базы не приносят пользы и не вводятся.

## Решение по SQLite

**В Phase 2 SQLite не вводится, миграции пользовательских файлов нет.**
После Phase 1 CSV уже не является источником истины: содержимое хранится в файлах,
метаданные объектов восстанавливаются из этих файлов, CreationTime нового бакета
сохраняется в `.bucket.json`. Сама по себе SQLite не создаёт общей транзакции с
filesystem. Её добавление сейчас потребовало бы журнала согласования двух
хранилищ при отсутствии функций, которым нужны самостоятельные метаданные.

Вернуться к SQLite стоит при необходимости custom metadata, тегов, устойчивых
квот, поиска или если измеренный startup scan становится неприемлемым. Решение
должно включать:

1. Остановку writer и проверенную резервную копию всего каталога.
2. Версионированную схему, dry-run импорта и сверку числа/размеров объектов.
3. Протокол pending → staged → committed и recovery после каждого crash window.
4. Проверку restart/crash/restore и совместимости API до переключения.
5. План отката с учётом новых записей; простого возврата старого бинарника мало.

До появления этих требований используем один источник истины и сохраняем
существующие ограничения: один процесс, локальная filesystem, in-memory индекс,
сканирование при запуске. Горизонтальное масштабирование не заявляется.

## Commit и recovery

PUT:

1. Проверка context/имён/бакета, резервирование upload slot и счётчика бакета.
2. Поток в приватный staging-файл с лимитом; `Sync` и `Close`.
3. Под общей блокировкой: повторная проверка context и назначения, atomic rename.
4. Обновление индекса и синхронизация директорий.

До rename старый объект сохраняется. После rename объект опубликован;
ошибка fsync или потерянный ответ означает неопределённый для клиента результат.
После restart индекс строится из опубликованных файлов, staging очищается.
Обычные файлы не переписываются при открытии хранилища.

DELETE удаляет файл и обновляет индекс под одной блокировкой, затем синхронизирует
каталог. Удаление бакета проверяет индекс, uploads и фактические записи каталога;
рекурсивное удаление не используется. Process lock исключает второго writer.

Публикация/удаление и индекс остаются в одном компоненте. Рефакторинг не переносит
часть commit в сервис и не обещает транзакции между независимыми backend-ами.

## Ошибки, безопасность и тесты

Сервис добавляет имя операции через `%w`; `errors.Is` сохраняет исходную причину.
HTTP выбирает стабильные публичные сообщения по классу ошибки: подробности
вложенного backend error не попадают в ответ. Контекст запроса, его значения и
deadline передаются до repository; отменённые операции не вызывают его.
Файловый backend также проверяет входные данные как отдельную защитную границу.

Общий токен по-прежнему даёт доступ ко всему экземпляру для доверенных клиентов.
Многопользовательские ACL, S3, streaming GET, HEAD, Range и ETag не добавляются
в этом этапе.

Проверки включают прежние regression/crash/race сценарии, независимые service
и HTTP тесты, стабильность XML, чтение Phase 1 JSON без перезаписи, одинаковые
ключи в разных бакетах и сохранение DataDir при смене рабочего каталога.

Для перехода с Phase 1 достаточно остановить сервер и запустить новую сборку
с теми же настройками и каталогом. Резервное копирование остаётся эксплуатационным
требованием; автоматической миграции или преобразования пользовательских файлов нет.

## Дополнение Phase 3

`Repository.OpenObject` / `Service.OpenObject` возвращают доменный `Download`:
метаданные версии и `ReadSeekCloser`, который обязан закрыть вызывающий код.
HTTP управляет Range/условными запросами, а storage — временем жизни дескриптора,
checksum и лимитом потоков. HTTP не получает физический путь и не использует
`ServeFile`. Блокировка индекса защищает выбор версии и открытие файла, но
не удерживается во время передачи или хеширования.

SHA-256 новых объектов считается при записи и публикуется в индексе вместе
с rename. В Phase 3 индекс лениво дополнялся checksum при открытии;
перед кешированием проверяется идентичность inode текущего пути и дескриптора,
чтобы конкурентная замена не получила checksum старой версии. Формат хранения
не менялся. Ранее перечисленные ограничения Phase 2 по GET/HEAD/Range/ETag
сняты; ACL и внешний S3 backend остаются за рамками этой реализации.

По выбранному пользователем контракту обычный GET скачивает файл,
а `?metadata=1` возвращает прежний XML. Это требует обновления существующих
клиентов метаданных. PUT, DELETE и операции бакетов сохраняют контракт.

## Дополнение Phase 5

HTTP middleware владеет request ID, событием завершения и RAM-метриками.
`Options.Logger` позволяет внедрить `slog.Logger` без глобального состояния
в HTTP-тестах. Registry создаётся отдельно для каждого `httpapi.New`, не глобально.
`/-/metrics` находится внутри существующей авторизации; сбор snapshot не
удерживает mutex во время сетевой записи. Данные и идентификаторы объектов
не включаются в labels или сообщения. Repository/domain не зависят от exporter.
Метрики отражают HTTP-операции, не прямые вызовы storage вне HTTP.

## Дополнение Phase 6

`ListObjects` и `Usage` добавлены в consumer-owned interfaces service/HTTP.
Repository возвращает доменные страницы и usage, HTTP отвечает за query parsing
и XML. Listing использует ограниченный heap поверх существующего индекса,
без добавления базы данных. Usage хранится в RAM и восстанавливается из файлов.

Проверка квот и изменение счётчиков происходят в одной критической секции
с rename/remove и изменением object index. Перезапись учитывает текущую
опубликованную версию; нет отдельной транзакции счётчиков или новой persisted
metadata на этапе Phase 6. Последующее durable object metadata описано ниже.
Неприменённые uploads не занимают логическую квоту, но занимают staging
на диске. Квоты по умолчанию отключены и не меняют запуск существующего хранилища.

## Восстановимые metadata объектов

Актуальный вариант сохраняет производные object metadata в
`.triple-s/metadata` через versioned/checksummed JSON и atomic rename.
Fingerprint inode/device/ctime + size/mtime связывает запись с конкретным blob.
Blob остаётся источником истины; запись metadata после commit может быть
восстановлена при следующем старте. Квоты/usage по-прежнему пересчитываются из
файлов, а не из отдельного авторитетного счётчика. SQLite не добавлен.

[Подробный протокол, миграция и ограничения](recoverable-metadata.md).

## Согласованная фиксация PUT/DELETE

`transaction.go` добавляет durable decision/redo protocol поверх blob и metadata.
Publication lock удерживается до journal cleanup и обновления RAM/usage.
После ошибки зафиксированного решения `stateError` блокирует операции до restart.
`Open` сначала выполняет replay, затем очищает staging и строит индекс.
[Протокол и границы гарантии](object-commit.md).

## Многопользовательская модель

`access` проверяет startup-only JSON registry (ID, role, SHA-256 токена, disabled).
Composition root открывает Store каждого namespace под общей процессной
блокировкой. HTTP после authentication выбирает service/Store пользователя;
администратор может явно выбрать namespace. Domain/repository не получают
пользовательские paths или ACL и сохраняют прежний протокол записи.
Это граница для внешнего HTTP; прямые внутренние вызовы Store доверенные.
Общий HTTP admission ограничивает нагрузку всех namespaces, usage/квоты scoped.
[Контракт, миграция и ограничения](multiuser-access.md).

Совместный доступ реализован через `sharedOperations`: явный декоратор всех
методов application boundary. Для выбранного владельца он проверяет bucket grant,
фильтрует ListBuckets, запрещает общую Usage и управление бакетами. Создание нового
метода Operations требует явной реализации в декораторе (compile-time assertion).
Неограниченный Store владельца не передаётся HTTP-handler приглашённого пользователя.

## Cluster backend

`internal/cluster.Repository` реализует прежний service.Repository, используя
PostgreSQL как точку публикации ссылок на immutable S3 blobs. API не хранит индекс
или credentials локально. `httpapi.Authority` читает текущего пользователя/grants
и выбирает namespace на каждый запрос; sharedOperations по-прежнему ограничивает
совместный доступ. SQL namespace row lock обеспечивает атомарные usage/квоты.
[Протокол, схема, migration и operational limits](horizontal-scaling.md).
