# Observatory: живая панель проекта

Панель встроена в Go-бинарник и доступна на `http://127.0.0.1:8080/-/observatory`.
Она работает с реальным API того же сервера. Отдельный сайт на Sites остаётся
концептуальной симуляцией и не получает административный токен вашего проекта.
Установка Node.js, сборка frontend и внешние CDN для панели не нужны.

## Запуск

Локальный режим: обновите бинарник, запустите обычной командой с прежними
`--dir`, токенами и ограничениями; откройте `/-/observatory` и введите токен
администратора. Объём включает административное и все подключённые пользовательские
пространства. Старые не подключённые к текущему реестру пространства в эту сумму
локального режима не входят. В cluster mode сумма берётся из всех `ts_namespaces`.

Для **уже инициализированного** Compose-кластера, в терминале с прежними переменными:

```sh
docker compose -f deploy/cluster/compose.yaml build api admin
docker compose -f deploy/cluster/compose.yaml run --rm admin enable-observatory
docker compose -f deploy/cluster/compose.yaml up -d --scale api=3 api gateway
```

`enable-observatory` — отдельная идемпотентная миграция: создаёт только таблицу
`ts_observatory_nodes` и её индекс. Повторный `init` не нужен. У нового кластера
таблица уже создаётся при `init`. API не выполняет DDL автоматически.
При отдельной runtime-роли после миграции DBA должен выдать:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON ts_observatory_nodes TO triples_api;
```

Миграция идёт через operator credentials. Имеющийся пример ролей обновлён в
`deploy/cluster/database-roles.sql`. До миграции сервер продолжает работу;
панель сообщает `registry_migration_required` и показывает текущий процесс.

Откройте `http://127.0.0.1:8080/-/observatory`. Можно открыть и через ваш TLS ingress.
Введите существующий admin Bearer token (например, содержимое `operator.token`).
Обычный пользователь, включая пользователя с bucket grant, получает 403 на данные.
Реестр PostgreSQL проверяется на каждом опросе: отзыв/disabled применяется как к API.

## Что измеряется

| Показатель | Источник и значение |
| --- | --- |
| RPS | Завершённые HTTP-операции, окно до 10 секунд на реплику; сумма доступных реплик |
| Latency | Среднее время завершённых HTTP-запросов того же окна; не p95 |
| Connections | TCP connections из `http.Server.ConnState`, включая idle keep-alive и соединения панели |
| In flight | Текущие пользовательские HTTP-запросы; опросы панели и metrics исключены |
| Storage usage | Опубликованные логические байты, объекты и бакеты; не физическая ёмкость S3 |
| Pending / retired / deleting | Состояния blob ledger PostgreSQL; в local mode — 0, ledger этого формата там нет |
| Реплики | Случайный ID процесса; новый ID при перезапуске; heartbeat PostgreSQL каждые 5 секунд |
| PostgreSQL health | Реальный запрос к writer, проверка read-only/recovery, длительность проверки |
| S3 health | Реальный SDK HeadBucket с таймаутом 1.5 секунды; не обещание работоспособности всех S3 операций |
| Local health | Проверка Usage через подключённые локальные stores |

Snapshot обслуживается из памяти, обновление браузера — каждые 2 секунды;
сбор зависимостей и публикация heartbeat происходят отдельно от PUT/GET.
Один sample имеет общий таймаут 4 секунды. На каждую реплику добавляется один
HeadBucket примерно каждые 5 секунд и небольшие SQL-запросы; учитывайте это
при большом числе реплик и расчёте S3 request costs.

Реплика без heartbeat более 15 секунд помечается `stale`, её текущая нагрузка
исключается из сумм. Это означает отсутствие свежего heartbeat, а не доказанный
отказ процесса или факт исключения upstream самим Nginx. После нового heartbeat
состояние восстанавливается. Offline записи удаляются через час. API ограничивает
реестр 64 недавними процессами, диаграмма показывает первые 12; счётчики считают
все процессы в snapshot. Синхронизируйте часы узлов для читаемого порядка событий;
возраст heartbeat рассчитывает PostgreSQL, а не часы браузера.

## События, анимация и границы наблюдения

Каждая реплика держит последние 24 завершённых события в памяти и публикует их
в heartbeat; браузер показывает 12 последних событий со всех доступных реплик.
Поля: серверный Request ID, sequence, операция, время, HTTP status/outcome,
длительность и число прочитанных/отправленных байтов. При высокой нагрузке часть
событий между опросами не попадёт в выборку. Счётчики продолжают учитывать все
завершения. Это не долговечный audit log и не distributed tracing.

Синие/фиолетовые потоки иллюстрируют **новые реально завершённые операции**,
а не проигрывают случайные запросы. Отдельные внутренние hops/SQL commit/S3 SDK
попытки не трассируются. При reduced motion потоки отключены, данные обновляются.
Пауза и скрытие вкладки останавливают опрос браузера, не останавливая сервер.

Фактическая архитектура: `Client → ingress/direct → API replicas → PostgreSQL + S3`.
Приложение не реплицирует blobs между API-репликами. Внутреннее устройство
S3/MinIO, erasure coding, replication lag и физические диски эта панель не видит.
Replication/backup и сам Nginx отмечены как не наблюдаемые: источники их метрик
в проекте пока не подключены. Панель не создаёт backup и не запускает GC.

## Контракт и безопасность

- `GET /-/observatory`, `GET /-/observatory/app.js`, `GET /-/observatory/style.css`:
  публичная оболочка входа и фиксированные локальные assets, без данных проекта.
- `GET /-/observatory/state`: admin-only JSON, schema version 1. HEAD поддержан;
  остальные методы — 405. Нужен ровно один `Authorization: Bearer …`; query token
  и cookie не являются учётными данными. CORS не включается.
- Токен хранится только в памяти вкладки, очищается из password field после входа,
  не попадает в localStorage/sessionStorage, URL или iframe другого origin.
- CSP разрешает только same-origin scripts/styles/connect; inline scripts, CDN,
  embedding в чужие frames и отправка форм запрещены. Ответы `no-store`, `nosniff`.
- Нет имён бакетов/объектов, пользовательских ID, DSN, endpoint credentials,
  заголовков, тел файлов и raw error strings в telemetry.
- При ошибке/таймауте обновления данные помечаются устаревшими. Через 15 секунд
  текущие показатели скрываются. При недоступной PostgreSQL авторизация cluster
  mode остаётся fail-closed: 503 и состояние «нет связи», без token fallback.
- TLS и защита operator credentials настраиваются как для существующего API.

`version`, `mode`, `at`, `sampled_at`, `registry`, `nodes[]`, `database`,
`object_store`, `storage`, `replication`, `backup` — поля JSON snapshot.
Каждый `nodes[]` имеет `id`, `started_at`, `age_seconds`, `state`, `rps`,
`latency_ms`, `inflight`, `connections`, накопительные counters и `events[]`.
Это внутренний административный контракт; права на пользовательские объекты
он не расширяет.

## Проверка

`go run ./tests -race ./...` проверяет privacy, auth, polling isolation, ограниченность
событий и конкурентное чтение. Cluster integration проверяет общий реестр двух
реплик, устаревший/восстановленный heartbeat и миграцию старой схемы.
Браузерная проверка выполняется на реальном локальном Go-сервере: PUT/DELETE
обновляют usage и события; токен не сохраняется; проверены вход, пауза, выход
и адаптивная компоновка.
