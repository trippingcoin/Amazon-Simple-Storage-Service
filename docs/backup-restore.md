# Проверяемые резервные копии

Рекомендуемый способ — встроенная offline-утилита `triple-s-backup`. Она создаёт
архив и манифест, а затем действительно восстанавливает копию во временный каталог
и проверяет каждый объект. Успех означает проверку конкретной копии, а не только
успешное выполнение tar.

## Команды

```sh
go build -o /tmp/triple-s-backup ./cmd/triple-s-backup

# Штатно остановите сервер. Родительские каталоги должны существовать.
/tmp/triple-s-backup create \
  --dir /absolute/path/data \
  --out /absolute/path/backups/backup-unique-name \
  --work-dir /absolute/path/verification-work

# Повторная проверка существующей копии, например после переноса на другой диск.
/tmp/triple-s-backup verify \
  --backup /absolute/path/backups/backup-unique-name \
  --work-dir /absolute/path/verification-work

# Восстановление только в новый каталог; автоматического переключения сервера нет.
/tmp/triple-s-backup restore \
  --backup /absolute/path/backups/backup-unique-name \
  --to /absolute/path/new-restored-data
```

`--work-dir` необязателен: по умолчанию используется системный временный каталог.
Для больших хранилищ задавайте диск с достаточным свободным местом. Нужны место
под несжатый архив и отдельную полную восстановленную копию. Backup и рабочий
каталог проверки должны находиться вне исходного хранилища.

Все команды возвращают JSON `status: verified` с SHA-256, временем создания,
числом пространств/бакетов/объектов и суммой байтов объектов. Exit code 0 означает
успех; ошибка возвращает ненулевой код без успешного JSON. Результат проверки
можно сохранить как отдельный отчёт. Команды ничего не отправляют в сеть.
Планировщик, удалённое хранение, retention и переключение клиентов не добавлены.

## Что проверяется

1. `create` получает существующие файловые блокировки legacy Store и всех
   пользовательских пространств, включая отозванные/удалённые из реестра.
   Работающий сервер приводит к отказу. Перед копированием выполняется штатное
   recovery: ранее зафиксированные решения PUT/DELETE могут быть завершены,
   производные metadata — восстановлены. Это не побайтовый forensic snapshot.
2. Формируется детерминированный SHA-256 inventory: идентичности пространств,
   бакеты (включая пустые), время создания, объекты, размер, MIME, время изменения
   и SHA-256. Содержимое каждого объекта читается потоково и сравнивается с его
   восстановленной metadata. Весь объект в RAM не загружается.
3. Под блокировками записывается весь каталог, включая private metadata,
   journals и каталоги tenants. `data.tar` и `manifest.json` синхронизируются
   на диск. Новые каталоги имеют 0700, файлы — 0600. Существующий backup не заменяется.
4. Блокировки исходного хранилища освобождаются после снимка. Проверка дальше
   работает только с независимой копией. `create` сообщает успех только после
   полного пробного восстановления и сравнения inventory.
5. `verify` и `restore` проверяют версию/структуру манифеста, размер и SHA-256 tar.
   Хеш повторно вычисляется по тем же байтам, которые распаковываются, чтобы
   обнаружить изменение архива между проверкой и извлечением.
6. Распаковка разрешает только обычные файлы и каталоги. Абсолютные пути,
   `..`, дубли, symlinks, hardlinks и специальные файлы запрещены. Запись идёт
   через `os.Root` в новый приватный каталог без перезаписи. Число записей
   ограничено миллионом, сумма распакованных данных — размером несжатого архива.
7. В восстановленной копии выполняются настоящее recovery и потоковое чтение
   всех объектов. Inventory digest и счётчики должны совпасть с манифестом.
   Временная копия после `verify` удаляется. Неудачный `restore` удаляет только
   созданный им новый каталог; исходные данные и backup сохраняются.

Общие бакеты остаются в пространстве владельца; они не дублируются в backup
получателей доступа. Копируются все пространства, а не только текущие активные ID.
Изменения источника после создания копии не влияют на её проверку.

## Формат и ограничения

Backup — каталог с двумя обязательными файлами:

- `data.tar`: несжатый PAX tar с точностью mtime до наносекунд;
- `manifest.json`: версия 1, SHA-256 архива, SHA-256 логического inventory и счётчики.

Inventory version 1 зависит от текущего формата доменных metadata; изменение
его сериализации требует совместимого reader или новой версии backup.
Ручной tar без манифеста этой утилитой не проверяется. Поддерживаются локальные
файловые системы, на которых работает существующий Store (macOS/Linux).

SHA-256 обнаруживает повреждение, но **не является подписью**: замена одновременно
архива и манифеста злоумышленником с доступом к backup может пройти проверку. Защищайте
копии правами доступа и храните отдельно доверенный checksum/отчёт; для защиты от
умышленной подмены нужен внешний механизм подписи или неизменяемого хранения.
Проверка отражает состояние данных на момент снимка; она не может доказать, что
объект не был повреждён ещё до снимка и пересоздания его исходной metadata.

Реестр `--users-file`, права grants, токены и TLS-ключи находятся вне данных и
в этот backup не включаются. Сохраняйте их отдельно и при restore сохраняйте
постоянные user ID и актуальные решения об отзыве доступа. Утилита проверяет
данные, но не внешнюю конфигурацию авторизации, HTTP deployment или права OS owner
на другом хосте. Восстановление не запускает сервер и не переключает клиентов.

Ошибка/отмена удаляет создаваемую неполную копию; при SIGKILL или отключении питания
может остаться частичный каталог. Не считайте его успешным по наличию файлов:
запустите `verify`. Старые версии с open download, staging и служебные файлы могут
требовать дополнительного дискового пространства. Весь файловый индекс Store
восстанавливается в RAM; потоковая обработка не означает постоянную память
независимо от количества объектов.

## Проверки реализации

`internal/backup` тестирует create/verify/restore, multiuser и отозванные namespaces,
пустые бакеты/объекты, Unicode, независимость от изменения источника, отказ на
live source и существующих destinations, повреждение архива/манифеста, неверную
версию, отмену, unsafe tar paths/links/duplicates и потоковую обработку файла.
`cmd/triple-s-backup` проверяет команды и JSON результата. Они включены в обычный
`go run ./tests ./...` и существующий CI.

## Прежняя ручная процедура

Ниже сохранён способ ручного offline tar backup/restore. Он не создаёт манифест
встроенной утилиты и требует самостоятельной проверки восстановленных данных.

Поддерживаемая процедура — **offline backup** всего каталога `--dir`.
Сначала штатно остановите сервер и убедитесь, что процесс завершён и записи
больше нет. Не копируйте работающий каталог: файлы и `.bucket.json` могут
относиться к разным моментам. Не удаляйте lock-файл у работающего процесса.

Пример для macOS/Linux; подставьте собственные абсолютные пути. Каталог backup
должен находиться вне каталога данных. Все команды выполняются владельцем данных.

```sh
umask 077
storage_dir=/absolute/path/to/data
backup_dir=/absolute/path/to/backups
mkdir -p "$backup_dir"
# Уникальное имя: не перезаписывайте предыдущий backup.
archive="$backup_dir/storage-$(date -u +%Y%m%dT%H%M%SZ).tar"
tar -cpf "$archive" -C "$storage_dir" .
shasum -a 256 "$archive" > "$archive.sha256"
```

Проверьте успешное завершение каждого шага. После создания backup сервер можно
запустить на исходном каталоге. Архив содержит приватные объекты: ограничьте доступ,
храните отдельную защищённую копию, при необходимости используйте шифрование.
Токен и TLS-ключи из внешней конфигурации эта процедура не копирует: их необходимо
восстанавливать отдельно через используемый механизм управления секретами.

Восстанавливайте только доверенный архив в **новый пустой каталог**, при
остановленном целевом сервере. Не распаковывайте поверх существующих данных:
это может сохранить файлы, которых уже не было в backup.

```sh
shasum -a 256 -c "$archive.sha256"
restore_dir=/absolute/path/to/new-restored-data
mkdir -m 700 "$restore_dir"
tar -xpf "$archive" -C "$restore_dir"
```

При любой ошибке остановитесь. Запустите сервер с `--dir "$restore_dir"` и
отдельным loopback-портом; проверьте авторизованные список бакетов, XML metadata,
HEAD и скачивание контрольных объектов с SHA-256. Сравните их с заранее
сохранённым inventory/checksum манифестом, если он ведётся. Только после проверки
переключайте клиентов. Исходный каталог сохраняйте до подтверждения восстановления.

`.triple-s/lock` может присутствовать в архиве: блокировка привязана к процессу
и файловому дескриптору, а не к наличию файла. При остановленном источнике он
не мешает новому процессу. Права каталога должны остаться 0700; файлы не должны
стать доступными группе/остальным. На другом хосте отдельно проверьте владельца.
Tar может округлить mtime до секунды; ETag по содержимому сохраняется, а точность
Last-Modified HTTP и так составляет одну секунду.

`TestOfflineBackupRestore` выполняет эти tar-операции на временных данных,
проверяет независимость копии от дальнейших изменений источника и возможность
записи после восстановления. Это проверка процедуры, а не встроенная команда
backup, планировщик или гарантия восстановления конкретного production-архива.

После добавления durable object metadata backup также включает
`.triple-s/metadata`. При restore локальные inode/ctime меняются: сервер
перестроит записи из blob при старте, поэтому первый запуск может быть долгим.
Встроенные metadata не заменяют отдельный checksum архива. Подробнее —
[восстановление metadata](recoverable-metadata.md).

С журналом фиксации нельзя исключать `.triple-s/transactions` или upload staging
из backup. Остановленный snapshot с незавершённой операцией восстанавливается
через replay. Не смешивайте части разных backup и не удаляйте journal marker,
чтобы обойти ошибку запуска. См. [согласованную фиксацию](object-commit.md).

## Пользовательские пространства

После включения `--users-file` backup должен включать весь
`.triple-s/tenants` со всеми вложенными private metadata и journals.
Реестр пользователей сохраняйте отдельно; при restore сохраняйте постоянные ID
и актуальные решения об отзыве доступа. Старые токены/права из backup нельзя
активировать автоматически. [Подробности](multiuser-access.md).

## Cluster backend — отдельная процедура

Эта утилита и tar-процедура покрывают локальный backend. Для `--backend cluster`
нужны согласованные PostgreSQL/S3 backups; каталог API содержит только scratch.
`triple-s-cluster verify` проверяет текущие ссылки и SHA-256 после восстановления,
но не создаёт архив. [Retention, GC, restore и проверка](horizontal-scaling.md#backup-и-восстановление-кластера).
