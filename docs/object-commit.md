# Согласованная фиксация объектов

PUT и DELETE объектов используют durable redo journal. Он согласует blob,
дисковую metadata, RAM-индекс и логические квоты при сбое процесса. Общий
publication lock закрывает доступ новых читателей к промежуточному состоянию.
Это протокол восстановления, а не один атомарный системный вызов для двух файлов.

## Точка фиксации

До решения о фиксации сервер проверяет входные данные, лимиты/квоты и контекст.
Для PUT тело полностью записывается в приватный staging и синхронизируется.
Затем создаётся checksummed/versioned record со следующими полями: уникальный
ID, действие `put`/`delete`, логический ObjectID, размер, SHA-256 и metadata.
Произвольные filesystem paths в журнале не принимаются.

Запись подготавливается как `.triple-s/transaction-<id>` и после file sync
переносится в `.triple-s/transactions/<id>.json`. Sync исходного каталога
гарантирует сохранение upload staging **до** ссылки на него в решении.
Rename записи и успешный sync каталога transactions — durable commit decision.

| Состояние | Поведение |
|---|---|
| До решения | Старый объект остаётся действующим; ошибка/отмена очищает временные данные |
| Решение сохранено | Операция должна быть завершена; отмена запроса больше не откатывает её |
| Файл и metadata сохранены | Журнал удаляется, каталог журнала синхронизируется |
| Завершение | RAM-индекс и usage обновляются под той же блокировкой; API возвращает успех |

PUT после решения публикует файл и metadata. DELETE удаляет файл и metadata.
Оба шага синхронизируют соответствующие каталоги. RAM не объявляет операцию
успешной раньше завершения протокола. Старые уже открытые download descriptors
продолжают читать свою неизменную версию — это не чтение частичного commit.

## Ошибки после решения

Если rename, metadata write, directory sync или journal cleanup завершились
ошибкой после появления решения, хранилище переходит в `recovery required`.
Ответ API — **503, `storage recovery required`**. Другие операции над состоянием
(GET/HEAD, списки, usage, PUT/DELETE и операции бакетов) также получают 503 до
перезапуска. Уже начатые uploads не могут создать следующее решение; их staging
очищается, если он не принадлежит зафиксированной операции. Метрики остаются доступны.

Это сознательный выбор согласованности вместо доступности после ошибки диска.
Простое повторение запроса до restart не помогает; автоматического восстановления
во время обслуживания запросов нет. Уже открытые streams и shutdown продолжают
работать. Если процесс завершился после появления marker, но до успешного sync,
результат также неопределён: recovery завершит решение, если оно сохранилось.

У клиента может отсутствовать успешный ответ, хотя операция уже зафиксирована.
После восстановления нужно проверить объект/ETag и затем решить, нужен ли retry.
Это не exactly-once API и не дедупликация повторов по клиентскому idempotency key.
DELETE при повторе после завершения удаления по-прежнему может вернуть 404.

## Recovery

Восстановление выполняется при `Open`, под process lock, **раньше** очистки upload
staging, сканирования объектов и восстановления derived metadata:

1. Проверяются приватный каталог журнала, имена, regular-file type, лимит 16 KiB,
   версия envelope/record, digest, действие и валидность logical IDs.
2. Для PUT с существующим staging проверяются размер и SHA-256, затем выполняется
   публикация. Если staging уже отсутствует, проверяется SHA-256 опубликованного
   файла: так определяется, что rename успел выполниться.
3. Для DELETE при существующем файле проверяется ожидаемый checksum, затем
   выполняется удаление; отсутствие файла является допустимым повторным состоянием.
4. Metadata дописывается/удаляется, каталоги синхронизируются, marker удаляется
   с directory sync. Только затем обычный recovery восстанавливает RAM/usage.

Replay идемпотентен: повторный сбой в процессе восстановления оставляет решение
для следующего запуска. Допустимо не более одного незавершённого marker: runtime
использует глобальный publication lock и блокирует дальнейшие операции после
неудачного commit. Несколько marker не сортируются произвольно — запуск отклоняется.

При неизвестной версии, испорченном JSON/digest, небезопасном пути/symlink,
пропавшем или несовпадающем staging/blob запуск прекращается. Журнал и оставшиеся
данные сохраняются; система не угадывает, какую версию считать правильной, и
не удаляет evidence как обычный временный мусор. Проверка payload checksum
при replay отличает этот журнал от восстановимого metadata cache.

## Эксплуатация и совместимость

При `recovery required` остановите сервер, устраните проблему прав/диска,
сохраните offline-копию **всего** `--dir` и запустите ту же или совместимую сборку.
Если журнал повреждён, используйте проверенный согласованный backup/ручной разбор;
не удаляйте marker для обхода ошибки. Нельзя смешивать журнал и staging из разных
снимков. После успешного старта проверьте HEAD/ETag, listing и usage.

Offline backup включает `.triple-s/transactions` и staging. Даже snapshot
остановленного процесса с незавершённым решением может быть восстановлен в
новом каталоге: replay проверяет байты и создаёт metadata с новой локальной
file identity. Копирование работающего каталога не поддерживается.

Формат blob и HTTP-успехов не менялся. Новый служебный каталог создаётся
автоматически. Старый бинарник без поддержки журнала использовать на этом
layout нельзя; для отката нужна отдельная offline-копия до обновления.
Production-данные при реализации не изменялись.

## Границы гарантии

- Протокол распространяется на отдельные PUT/DELETE объектов. Batch transactions
  и создание/удаление бакетов им не заменены.
- Только один процесс и локальная поддерживаемая файловая система. Внешнее
  редактирование файлов/журнала во время работы не поддерживается.
- Нужны реальные гарантии file/directory fsync и atomic rename файловой системы.
  Сбой процесса проверен; неисправный диск/контроллер и потеря питания не эмулировались.
- Потерянные байты не восстанавливаются из журнала: checksum проверяет staging/blob,
  но сам payload файла в JSON не дублируется. Нужен backup.
- Journal checksum не является криптографической авторизацией против владельца
  диска, способного переписать record вместе с digest.
- Дополнительные file/directory sync увеличивают стоимость записи. Глобальная
  блокировка публикации сохраняется; ускорение/production throughput не обещаются.

## Проверки

`transaction_test.go` содержит crash matrix для PUT/DELETE на пяти границах:
prepared, durable decision, blob, metadata, finished. Проверяются версия файла,
SHA-256, metadata, usage, очистка staging/journal и повторный restart.
Дополнительно проверены:

- ошибка публикации после решения и блокировка всех операций над состоянием;
- отсутствие промежуточной версии у новых читателей и сохранность pinned stream;
- отмена до и после решения;
- параллельный upload после неудачной фиксации;
- truncated/digest/future-version/path/symlink/multiple-record повреждения;
- потерянный и повреждённый staging без автоматического удаления evidence;
- offline backup/restore с незавершённым решением;
- HTTP mapping 503 без раскрытия внутренней ошибки.

Полная локальная матрица с `-race -tags=integration,stress`, vet и сборки
macOS/Linux прошли. Новые тесты включены существующими CI-командами.
